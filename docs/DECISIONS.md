# Decisions

Short records of choices that are costly to rediscover. Add one when a decision changes scope, method or interfaces. Format: what, why, consequence. Newest last.

**D1. Spring Boot 4.1.x, Java 21.** Boot 3.2 is out of open-source support; a deliberately EOL stack would look careless. Re-verify the exact patch before Week 2 module work.

**D2. Two LLM agents, deterministic Selector.** The Planner emits capability IDs from a closed vocabulary, so choosing modules is a lookup plus a compatibility check; an LLM would add cost and noise. An LLM-Selector variant is parked as a Phase 2 ablation.

**D3. Controlled coverage ablation instead of a reuse-rate scatter.** Reuse rate is an outcome, not a controlled variable. Running "Ours" at registry sizes k = 0/2/4/6 on the same prompts gives a real x-axis. Orders are pre-registered (`vocab.py`).

**D4. Baseline C (skills only, no deterministic composer).** Without it we cannot tell whether gains come from composition or merely from having skills.

**D5. Registry cut from 9 to 6 modules; prompts from 10 to 8.** Oracle writing is the real cost. `observability.actuator` and `database.flyway` are provided by `deployment.docker`. Rate-limit is Phase 2.

**D6. "Uncovered" capabilities are valid.** A capability in the vocabulary with no registry module is not an error; it becomes generation work. This is what makes the ablation possible. (Changed from the first draft, which rejected them.)

**D7. One pinned model for every strategy; independent repetitions.** Mixing models confounds the comparison. Seeds mean repetition index only, because providers do not guarantee seeded determinism.

**D8. Frozen blueprint for the main comparison.** One Planner run per prompt, hashed and committed, so differences between k levels are not Planner noise. A live-Planner run is secondary.

**D9. Shared application contract.** Every prompt carries the same externally visible API/UI contract (ports, login, REST shape, seeded users) so black-box oracles can score any strategy. Source of truth: `docs/benchmark-design.md` §5; Baseline A loads it from there.

**D10. Invalid runs are re-run, never imputed.** Missing usage data, missing cost, truncated output or unsafe paths mark a run invalid. No estimated metrics anywhere.

**D11. Global `*` permission is rejected when any entity is read-only.** `*` would grant writes to it; roles must list permissions explicitly. Enforced by `E_PERMISSION_READONLY`.

**D12. SKILL.md follows the open Agent Skills format.** Frontmatter `name` (module id with `.` → `-`) and `description`, body ≤ 400 tokens, fixed section order, mandatory "Do NOT" line. Keeps modules usable in other agents and feeds the reuse-violation checker.

**D13. Agent handoff files.** `CLAUDE.md` (entry point, rules, commands), `docs/PROGRESS.md` (status, next steps), this file (why). Purpose: a new agent reads about 150 lines instead of the whole repo.

**D14. The JWT module owns login; the app supplies users.** The module provides the token service, `POST /api/auth/login`, the password encoder and the only `SecurityFilterChain`. The app (Composer) supplies a `UserDetailsService` and seeded users. No database dependency in the module, so it stays testable without PostgreSQL. Trade-off: the Composer still writes the user entity and store.

**D15. Module tests live in `tests/java/`, wired by `testSourceDirectory`.** Keeps the registry layout from `module-spec.md` (`module/` = shipped code, `tests/` = proof) while `mvn verify` still runs from `module/`.

**D16. Spring Boot pinned to 4.1.1 in module POMs.** 4.1.0 (2026-06-10) built green first; 4.1.1 (2026-08-20) was the latest patch found on 2026-11-03. Module POMs import the Boot BOM instead of using a parent.

**D17. The JWT filter is not a Spring bean.** A `Filter` bean is also registered by the servlet container, so it would run twice. It is created inside the `SecurityFilterChain` bean method instead. Extra rules go through the `SecurityConfigurer` hook, which runs before the base rules (`anyRequest().authenticated()` must come last).

**D18. CORS lives in the JWT module for now.** The frontend (port 3000) calls the backend (port 8080) from a browser, so the first module that touches the filter chain must allow it. Origins are configurable (`allowed-origins`). The CORS source is built inside the chain method and is **not a bean**: Spring MVC registers `HandlerMappingIntrospector`, which is itself a `CorsConfigurationSource`, so a bean of that type from this module is skipped by `@ConditionalOnMissingBean` and the chain gets the MVC one, which has no CORS settings for `/api/**` (CI runs 2 and 3: preflight returned 200 with no headers). Revisit when `deployment.docker` exists.

**D19. RBAC works from URL shape, not annotations; modules depend on each other as Maven artifacts.** `authorization.rbac` turns `roles` and a `path -> resource` list into ordered `requestMatchers` rules (GET/HEAD read, POST/PUT/PATCH write, DELETE delete, `GET .../export.csv` export, then a deny-all per resource), added through the JWT module's `SecurityConfigurer` hook. Reason: deterministic, testable without controllers, and the Composer cannot forget an annotation. Trade-off: it only protects the resources listed in config, and `write` does not imply `read`. It depends on `com.mortar:jwt-auth`, so CI uses `mvn install` and builds `authentication.jwt` first, then the other modules in directory order (a directory-order-only loop failed when `audit.logging` sorted before `authentication.jwt`). The Assembler will have to supply those jars (Week 4).

**D20. `crud.pagination` is a base class the app subclasses, over Spring Data JPA.** `CrudController<T, R>` implements the contract's list, get, create, update and delete once; the app adds a one-line subclass per entity plus the entity and repository. Choices: `Long id`; POST 201, PUT 200, DELETE 204, unknown id 404 (added to `benchmark-design.md` section 5 before oracle freeze); `size` above the maximum and sort fields outside a per-entity whitelist return 400 instead of being clamped or passed to the database; `q` is a case-insensitive plain-text contains with LIKE wildcards escaped; unsorted lists order by `id` so paging is stable. `sort` is read from the raw parameter map because Spring would split `name,desc` into two values. The error advice applies only to `CrudController` subclasses so it cannot change other modules' responses. Trade-off: it needs a JPA datasource, so the module cannot be used on a non-JPA app.

**D21. Audit is a request filter inside the security chain, written synchronously, keyed on URL shape.** `audit.logging` watches `POST /api/<path>`, `PUT` and `DELETE /api/<path>/<id>` for the configured paths and records a row only after a 2xx answer from a signed-in user. It sits after the authorization filter, so rejected requests never reach it. The new id on create is read from the `Location` header (so `crud.pagination` now returns one). Why not `@Audited` annotations or AOP: they require every controller to opt in and would tie the module to `crud.pagination`; a filter works for any controller. Why synchronous (the context doc said async): an async writer can lose records on shutdown and makes black-box oracles poll; at internal-tool volume a single insert is cheap. Known trade-off: the insert happens after the handler, so a failed insert is logged (`AUDIT RECORD LOST`) but the client has already received its 2xx; the change and its audit row are not one transaction. The module adds its package through `@AutoConfigurationPackage` so `AuditLog` is scanned without disabling the app's own repository scanning. Schema: `audit_log` is created by Hibernate in v1; `deployment.docker` will have to own the migration (open item for that module).

**D22. `deployment.docker` ships files as module resources; Flyway owns module tables, Hibernate owns app tables.** The registry layout allows only `module/` for shipped code, so the Docker files live under `module/src/main/resources/mortar/deployment/` and the Assembler copies them to the repo root (`*.tmpl` files get `{{key}}` values from the module config). Defaults (health-only Actuator, `ddl-auto=update`, Flyway on) come from a `@PropertySource` so the app's own settings and environment variables always win. `V0_1__mortar_audit_log.sql` creates `audit_log` to match the `AuditLog` entity; the version is below 1 so an app's own `V1__...` migrations never collide. The app's own tables are created by Hibernate `update`, not migrations: the Composer would otherwise have to write correct SQL, a new failure source; this is not production-grade schema management and the report must say so. The JWT secret reaches the app as `MORTAR_AUTH_JWT_SECRET` (relaxed binding), empty when unset, so a missing secret fails at startup with the JWT module's message, while an app without JWT ignores it. Compose requires `POSTGRES_PASSWORD`, does not publish the database port, and waits for healthy db and backend. Open items: (1) generated apps depend on `com.mortar:*` artifacts that are in no repository, so the Assembler must vendor them into `backend/` before `docker build`; (2) the frontend Dockerfile assumes the React template provides `package-lock.json`, `npm run build` to `dist/` and `VITE_API_URL`.

**D23. The React template is one config file plus fixed code, with pinned dependencies.** The Assembler writes only `src/mortar.config.json` (schema `config.schema.json`); everything else is fixed, so frontend generation needs no LLM and no per-app code review. It uses a custom data provider for the contract (0-based pages, `sort=field,dir`, `q`, `{content,totalElements,page,size}`) rather than `ra-data-simple-rest`, which does not fit. Permissions are mirrored from the backend rules (`*`, `resource:*`, `resource:action`, exact) to hide controls only; the backend stays the authority. Because blueprints carry field names but no types, input types are inferred from names with an explicit override; author and timestamp fields are not editable and `update` sends the previous record underneath the edit so a PUT never wipes them. Versions are pinned exactly (React 18.3.1, react-admin 5.15.5, Vite 8, Vitest 5, TypeScript 5.9) and `package-lock.json` is committed because the frontend Dockerfile runs `npm ci`. `npm audit` flagged `decode-uri-component` (transitive via react-admin) as high severity; an npm `overrides` entry pins the patched 0.5.1 and CI fails on any high production advisory, so a future react-admin upgrade should drop the override once it no longer matters. Tests must import `Route` from `react-router-dom`, the same package react-admin imports, or the CommonJS/ESM split makes two copies of the router. Open: the kanban board is read-only and shows 100 records; no foreign-key lookups; real-stack verification waits for the Assembler.

**D24. The Selector is a pure function of blueprint and registry; pluralization has one definition.** `select(blueprint, registry, active)` returns a copy of the blueprint with `components` (dependency order, then ablation order) and `uncovered` filled, and a list of skipped modules with reasons. It fills each module config from blueprint values and validates it against the module's `config-schema.json`, so a bad config fails here, not in Maven. A module whose required capabilities are not provided by another selected module is skipped and its capabilities become uncovered (the same rule as `modules_for_k`; a test checks the two agree for k = 0, 2, 4, 6 on both orders). Conflicting capabilities, a Spring Boot or Java range mismatch (the module is skipped), no role holding `*` when `audit.logging` is selected, and two entities with the same URL path are explicit `SelectionError`s or skips, never silent. The URL path rule (`naming.py`) is shared by the backend module configs and the frontend config, and is written into `benchmark-design.md` section 5 before oracle freeze. The blueprint hash (`blueprint_hash.py`) excludes `components` and `uncovered`, so all k values for one prompt share a hash; every event carries it. Trade-offs: the irregular-plural table is deliberately tiny and must be extended with a test when a prompt needs a word; version ranges support only `>=`, `<=`, `>`, `<`, `==` comparators.

**D25. The Assembler vendors module sources and builds them inside the backend image.** The `com.mortar:*` artifacts are in no repository, so `assemble` copies each selected module's `module/` directory (pom and `src/main`, not tests) to `backend/vendor/<artifactId>/` and writes `backend/vendor/pom.xml`, a pom-packaging aggregator listing them. Maven's reactor orders them by dependency. The backend Dockerfile (module `deployment.docker`, changed) now runs `mvn -Dmaven.test.skip=true -f vendor/pom.xml install` before building the app, so no jar is committed and the app pom depends on ordinary coordinates. Rejected: merging module sources into the app (the modules' `AutoConfiguration.imports` files collide) and committing jars (binary blobs, version drift). Everything the Assembler writes is deterministic and logged with its SHA-256; it refuses a non-empty output directory. It writes: `backend/pom.xml`, `Application.java` in the blueprint's base package, `application.yml` (module settings from the validated configs), the vendor tree, the React template with `src/mortar.config.json` (`searchable` and `exportable` are true only when `crud.pagination` and `export.csv` are selected), and, only when `deployment.docker` is selected, the Compose file, Dockerfiles, nginx config, `.dockerignore` (root and both build contexts) and `.env.example`. When a module is not selected its files are simply absent, and its capability is in `uncovered` for the Composer. Spring Boot is pinned to 4.1.1 in the app pom (a test checks it equals every module POM). Not yet verified: that the generated backend compiles and the images build (needs Maven Central or Docker; first real check is the Week 5 validation stage).

**D26. Both agents go through one narrow model interface that forces a single tool call and refuses unmeasured responses.** `LlmClient.call_tool(system, user, tool)` returns the tool arguments plus input tokens, output tokens and cost; `LitellmClient` (litellm, imported lazily, same `MORTAR_MODEL` / `MORTAR_TEMPERATURE` / `MORTAR_MAX_OUTPUT_TOKENS` as Baseline A) raises `LlmError` on truncation, a wrong or missing tool call, missing usage, or a call it cannot price. Nothing is estimated. The Planner receives only the request text, the blueprint spec (read from `docs/blueprint-spec.md`, so the spec stays the single source) and the capability list; benchmark acceptance criteria never reach it. It submits the blueprint as a JSON object, and code, not the model, sets `apiVersion`, `kind`, the verbatim `metadata.prompt`, and empty `components` and `uncovered` (so the hash depends only on the plan). Validator messages go back to it for up to 3 attempts; every attempt's usage is kept. The Composer receives the blueprint, the entity paths, each selected module's SKILL.md (not its code), the uncovered capabilities, the stack line and the same contract text as Baseline A. Where it may write is enforced in code: under `backend/src/main/java/<basePackage>/` and `backend/src/main/resources/`, never over a file the Assembler wrote, plus the Docker files when `deployment.docker` is uncovered; anything else raises `ComposeError`. When a capability has no module, the Assembler adds the libraries its code needs to the pom (`UNCOVERED_DEPENDENCIES`). `generate` writes `run.json` with per-stage tokens and cost, and `built: false` until Week 5. Not verified: any real model call. The agents are tested with a fake client only; the prompts are untested against a model and will likely need a pilot-run revision before the 1-seed pilot (Week 6). Parked: the reuse-violation check (Week 5).

**D27. The MCP server is three read-only lookups, answered from contracts, never code.** `search_components`, `get_skill` and `get_dependencies` (the three named in `PROJECT_CONTEXT.md`) are plain functions in `mortar/registry/query.py` over the loaded registry, wrapped by `mcp-server/server.py`; nothing generates, writes or builds, and no tool returns module source (a test checks the summary fields and that `get_skill` returns the SKILL.md contract). Search is keyword scoring (module id words 3, tags 2, name, description, category and interface words 1, prefix match for terms of 3+ letters), ties broken by module id, so results are deterministic; it is not semantic search. `get_dependencies` resolves each required capability to the modules that provide it and gives the transitive module set, required env, conflicts, version ranges and Maven coordinates. The SDK is pinned (`mcp==2.3.0`, extra `mcp`); in 2.x an ordinary exception becomes an opaque "Error executing tool" for the client, so expected failures (unknown module) raise `ToolError`, which carries the message to the model. Tests drive the server with a real MCP client in memory and over stdio. Not verified: use from Claude Code or Cursor themselves (needs `claude mcp add`), and Python 3.12 on CI until the next run. Extra tools (select, assemble) are deliberately left out: they are scope creep until the benchmark needs them.

**D28. Reuse violations are static, per selected module, and declared by the module (`owns.imports`).** Every v1 module lists the library package prefixes it owns in `metadata.yaml` (JWT libraries for `authentication.jwt`, method-security packages for `authorization.rbac`, Envers and Javers for `audit.logging`, Spring Data REST for `crud.pagination`, CSV libraries for `export.csv`, Flyway for `deployment.docker`); the schema gained the optional `owns` object. `check_reuse` flags, in the Java the model wrote: an import under a selected module's owned prefix, a type declared with the simple name of a selected module's `provides.interface`, and a method returning `SecurityFilterChain` when `authentication.jwt` is selected. It works on comment- and string-stripped source so a mention in a comment is not a violation, and it reports file, line and the offending name. Modules that were not selected own nothing, so the same code is a violation at k=6 and not at k=0. The Assembler's own files are not checked (the Composer's are; those are what the metric is about). Reuse LOC uses a versioned counter (`loc-1`); `generate` writes `reuse_violations`, their details and `reuse{reused_loc, generated_loc, reuse_rate_loc}` into `run.json`. Trade-offs: it is name- and import-based, so a reimplementation under a new name (a hand-rolled JWT with the JDK's `javax.crypto`) is not caught, and a violation list is a lower bound; the limitations section must say so. `reuse_rate_tokens` is not implemented yet (needs the fixed tokenizer decision). Registry modules' metadata changed (the `owns` block only) before any benchmark run references them, which `module-spec.md` section 7 allows.
